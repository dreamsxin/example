# Firefox 130 字符串类型与编码转换源码分析

> 分析对象：Firefox 130.0.1 源码树。本文讨论 Gecko/XPCOM C++ 字符串，重点是
> `xpcom/string` 与 `intl/Encoding.h`。结论不应无条件套用到更早的 Firefox 分支。

## 1. 先记住三个相互独立的概念

Firefox 字符串代码最容易混淆的是把存储宽度、编码和内存所有权当成一件事。
实际应分别判断：

1. **代码单元宽度**：`char`（8 位）或 `char16_t`（16 位）。
2. **字节的编码语义**：ASCII、UTF-8、Latin-1、某种传统编码、原始二进制等。
3. **缓冲区属性**：是否拥有数据、是否以 NUL 结尾、是否有对象内联缓冲区。

核心结论如下：

- 名称中有大写 `C` 的 `ns[C]String` 家族存储 `char`；没有 `C` 的家族存储
  `char16_t`。
- `nsAString` 的内容按 UTF-16 代码单元解释，但允许暂时包含孤立代理项，因此是
  “可能无效的 UTF-16”，不是 UCS-2。
- `nsACString` 只是字节容器，**类型本身不保证 UTF-8**。其具体编码由 API 契约和
  数据来源决定。
- `Assign`、构造 `nsCString` 或取得 `.get()` 都不会自动转码。真正的转码必须由
  `NS_Convert*`、`Copy*`、`Append*` 或 `mozilla::Encoding` 等明确执行。

## 2. 模板层次与公开别名

公开的 8 位和 16 位类型由同一套模板分别实例化。别名定义见
`xpcom/string/nsStringFwd.h:64` 和 `xpcom/string/nsStringFwd.h:79`。

```text
mozilla::detail::nsTStringRepr<T>       只读表示和公共内存布局
  |
  +-- nsTSubstring<T>                   可变字符串 API；不承诺 NUL 结尾
        |
        +-- nsTString<T>                承诺 NUL 结尾，提供 get()
        |     |
        |     +-- nsTAutoStringN<T, N>  对象内联缓冲区
        |     +-- nsTDependentString<T> 非拥有、要求源缓冲区 NUL 结尾
        |
        +-- nsTDependentSubstring<T>    非拥有、不要求 NUL 结尾

nsTLiteralString<T>                     直接基于 nsTStringRepr<T>，布局兼容
nsTSubstringTuple<T>                    延迟拼接表达式，不拥有各片段
```

`nsTLiteralString<T>` 是一个重要例外：它并未真正继承 `nsTString<T>`，而是依靠相同
布局隐式转换为只读 `const nsTString<T>&`。这样静态字面量不需要生成析构代码。相关
实现见 `xpcom/string/nsTLiteralString.h:25`。

另外两个常见的辅助结果类型也不应被当成普通拥有型字符串：

- `Substring(aString, start, length)` 通常返回依赖原字符串的
  `nsDependent[C]Substring`，不复制字符。
- `PromiseFlatString(aString)` 把可能不以 NUL 结尾的 `nsA[C]String` 适配成
  `nsPromiseFlat[C]String`；源数据已经平坦且有结尾时可避免复制。它适合只在调用 C
  API 的短作用域内使用。
- `a + b` 产生 `ns[C]SubstringTuple` 延迟拼接表达式；赋给真正字符串时才统一复制，
  tuple 的生命周期不能超过被引用的片段。

### 2.1 常用类型对照

| 16 位类型 | 8 位类型 | NUL 保证 | 所有权和适用场景 |
| --- | --- | --- | --- |
| `nsAString` | `nsACString` | 不保证 | 参数和返回槽位的公共接口类型；通常用引用，不直接定义变量 |
| `nsString` | `nsCString` | 保证 | 通用可拥有字符串；可共享、复制或接管缓冲区 |
| `nsAutoString` | `nsAutoCString` | 保证 | 局部短字符串优先；默认对象内有 64 个代码单元的数组 |
| `nsDependentString` | `nsDependentCString` | 要求源数据已结尾 | 不复制且不拥有，源缓冲区必须活得更久 |
| `nsDependentSubstring` | `nsDependentCSubstring` | 不要求 | 不复制的区间视图，常由 `Substring()` 创建 |
| `nsLiteralString` | `nsLiteralCString` | 保证 | 静态字面量，通常通过 `u"..."_ns` / `"..."_ns` 创建 |

默认 `nsAuto[C]String` 的存储数组大小为 64，见
`xpcom/string/nsStringFwd.h:28`；其中一个位置留给 NUL，因此默认内联容量实际上是
63 个代码单元，见 `xpcom/string/nsTString.h:279`。超过容量后会使用堆缓冲区。

### 2.2 公共内存表示

`nsTStringRepr<T>` 的核心字段位于 `xpcom/string/nsTStringRepr.h:483`：

```cpp
char_type* mData;
LengthStorage mLength;
DataFlags mDataFlags;
ClassFlags const mClassFlags;
```

- `mData` 指向连续代码单元。
- `mLength` 是代码单元数，不是 Unicode 字符数，也不包含尾部 NUL。
- `mDataFlags` 描述当前缓冲区，例如引用计数、独占、内联、字面量、已终止等；依赖
  缓冲区主要表现为不具有任何所有权标志。
- `mClassFlags` 描述对象类别提供的保证，例如类是否要求 NUL 结尾。

字符串对象可在赋值或修改时切换缓冲区模式。例如 `nsString` 不应被简化理解为
“永远独占一块堆内存”；它可以共享引用计数缓冲区，随后在需要写入时取得可写存储。

### 2.3 常用类型之间如何转换

类型转换分成两类：

- **同宽转换**：例如 `nsString`、`nsAutoString`、`nsDependentString` 之间转换。
  字符编码不变，只改变对象类型或缓冲区所有权。
- **跨宽转换**：例如 `nsCString` -> `nsString`。这一定涉及编码解释，必须先确认
  8 位数据究竟是 UTF-8、Latin-1、传统编码还是二进制。

#### 2.3.1 同宽拥有型字符串与接口类型

`nsAString` / `nsACString` 主要是函数接口类型。具体字符串可以直接绑定到对应接口
引用，不发生复制或转码：

```cpp
void ReadWide(const nsAString& aText);
void ReadBytes(const nsACString& aBytes);
void WriteWide(nsAString& aResult);

void InterfaceExamples() {
  nsString owned(u"text");
  nsAutoString local(u"local");
  nsCString bytes("bytes");

  ReadWide(owned);   // nsString -> const nsAString&，不复制
  ReadWide(local);   // nsAutoString -> const nsAString&，不复制
  ReadBytes(bytes);  // nsCString -> const nsACString&，不复制

  nsString result;
  WriteWide(result); // nsString -> nsAString&，供函数写入
}
```

从接口值构造具体字符串，或赋给已有具体字符串：

```cpp
nsString MakeOwnedWide(const nsAString& aSource) {
  nsString result(aSource);
  return result;
}

nsAutoCString MakeLocalBytes(const nsACString& aSource) {
  nsAutoCString result;
  result.Assign(aSource);
  return result;
}
```

这仍是同宽赋值。字符串实现可能共享可共享的引用计数缓冲区，也可能复制数据；调用者
不应依赖具体策略。目标被修改时，字符串库会保证写入不会改变另一个逻辑字符串。
具体分支见 `xpcom/string/nsTSubstring.cpp:479`：引用计数缓冲区增加引用，静态字面量
继续引用原数据，其余来源通过普通 `Assign` 复制代码单元。

#### 2.3.2 `nsString` 与 `nsAutoString`

两者编码和公共 API 完全相同，可以通过构造或 `Assign()` 互转：

```cpp
nsString owned(u"Firefox");

nsAutoString local(owned);  // nsString -> nsAutoString

nsString copied(local);     // nsAutoString -> nsString

nsString assigned;
assigned.Assign(local);     // 覆盖式同宽赋值
```

8 位版本完全对称：`nsCString` <-> `nsAutoCString`。选择 `Auto` 只影响存储策略，不会
把字节验证为 UTF-8，也不会改变编码。

#### 2.3.3 拥有型字符串与 dependent view

从原始缓冲区或已有字符串创建非拥有视图：

```cpp
const char16_t rawWide[] = u"dependent";
nsDependentString wideView(rawWide);  // 要求 rawWide 已以 NUL 结尾

const char rawBytes[] = "bytes";
nsDependentCString byteView(rawBytes); // 要求 rawBytes 已以 NUL 结尾

nsString source(u"source");
nsDependentString sourceView(source.get(), source.Length());
```

从 dependent view 构造拥有型字符串：

```cpp
nsString ownedWide(wideView);
nsCString ownedBytes(byteView);
```

此方向会取得独立、可长期保存的字符串值。反方向只是保存源缓冲区指针；在 view 使用
期间，源数组或源字符串必须仍然存在，而且不能执行可能使缓冲区重新分配的修改。

源区间没有 NUL 结尾时使用 substring view：

```cpp
nsString source(u"0123456789");
const nsAString& view = Substring(source, 2, 4); // 指向 u"2345"，不复制

nsString ownedPart(view);                       // 需要独立保存时再复制
```

`Substring()` 结果同样依赖 `source` 的生命周期和缓冲区稳定性。

#### 2.3.4 字面量与普通字符串

字面量可直接传给接口，也可以构造拥有型或 auto 字符串：

```cpp
ReadWide(u"literal"_ns);                  // 字面量 -> const nsAString&
ReadBytes("content-type"_ns);             // 字面量 -> const nsACString&

nsString ownedWide(u"literal"_ns);        // 字面量 -> nsString
nsAutoCString localBytes("header"_ns);    // 字面量 -> nsAutoCString
```

这里仍不发生宽窄转换。`"..."_ns` 是 8 位字节，`u"..."_ns` 是 UTF-16。

#### 2.3.5 `nsAString` 与 NUL 结尾字符串

`nsAString` / `nsACString` 不保证结尾 NUL。当函数参数只有抽象接口，但 C API 需要
NUL 结尾缓冲区时，使用 `PromiseFlatString()`：

```cpp
void ConsumeWideBuffer(const char16_t* aBuffer);

void PassToC(const nsAString& aText) {
  const nsPromiseFlatString& flat = PromiseFlatString(aText);
  ConsumeWideBuffer(flat.get());
}
```

如果输入本来已平坦且有 NUL，`PromiseFlatString()` 可以避免复制；否则会创建临时
存储。不要把 `flat.get()` 保存到本函数之外。8 位接口对应使用
`PromiseFlatCString()` 和 `nsPromiseFlatCString`。

#### 2.3.6 8 位与 16 位类型的完整转换矩阵

| 源类型及语义 | 目标类型 | 正确方式 |
| --- | --- | --- |
| `nsCString` / `nsACString`，内容为 UTF-8 | `nsString` / `nsAutoString` | `NS_ConvertUTF8toUTF16` 或 `CopyUTF8toUTF16` |
| `nsString` / `nsAString`，内容为 UTF-16 | `nsCString` / `nsAutoCString`，目标为 UTF-8 | `NS_ConvertUTF16toUTF8` 或 `CopyUTF16toUTF8` |
| `nsCString`，内容为真正 Latin-1 | `nsString` | `NS_ConvertASCIItoUTF16` 或 `CopyASCIItoUTF16` |
| 已证明全部位于 `U+0000..U+00FF` 的 `nsString` | Latin-1 `nsCString` | `NS_LossyConvertUTF16toASCII` 或 `LossyCopyUTF16toASCII` |
| Windows-1252、GBK、Shift_JIS 等 `nsCString` | UTF-8 `nsCString` 或 UTF-16 `nsString` | `mozilla::Encoding::Decode*()` |
| UTF-8 `nsCString` 或 UTF-16 `nsString` | 某种传统编码的 `nsCString` | `mozilla::Encoding::Encode()` |
| 二进制 `nsCString` | 文本字符串 | 不能直接转换，必须先知道数据格式和字符编码 |

目标使用 `nsString` 还是 `nsAutoString` 不影响转码方式，因为两者都能作为
`nsAString&` 目标；8 位目标同理：

```cpp
void CrossWidthExamples(const nsACString& aUtf8,
                        const nsAString& aUtf16) {
  nsString ownedWide;
  CopyUTF8toUTF16(aUtf8, ownedWide);

  nsAutoString localWide;
  CopyUTF8toUTF16(aUtf8, localWide);

  nsCString ownedUtf8;
  CopyUTF16toUTF8(aUtf16, ownedUtf8);

  nsAutoCString localUtf8;
  CopyUTF16toUTF8(aUtf16, localUtf8);
}
```

不能使用普通 `Assign()` 或 `Append()` 代替上述跨宽转换：

```cpp
nsCString utf8;
nsString utf16;

// utf16.Assign(utf8);  // 错误：宽度不同，也没有说明 utf8 的编码
CopyUTF8toUTF16(utf8, utf16);
```

## 3. 字符宽度不等于字符编码

### 3.1 `nsAString`：可能无效的 UTF-16

`nsAString` 是 `nsTSubstring<char16_t>`。一个 Unicode 标量值可能占一个代码单元，
也可能以代理对占两个代码单元。因此：

- `.Length()`、索引、`Cut()`、`Substring()` 等都按 UTF-16 **代码单元**计数；
- 在任意代码单元位置截断可能拆开代理对；
- Gecko 为兼容 DOM/JavaScript，允许字符串中存在孤立代理项；
- 如边界要求有效 UTF-16，可调用 `EnsureUTF16Validity()`，它会把孤立代理项替换为
  `U+FFFD`，见 `xpcom/string/nsReadableUtils.h:413`。

### 3.2 `nsACString`：带外部编码契约的字节串

`nsACString` 是 `nsTSubstring<char>`。下面这些值都能放入同一类型：

- ASCII；
- UTF-8；
- Latin-1（每个字节值等于相同值的 Unicode 标量）；
- Shift_JIS、GBK、Windows-1252 等传统编码；
- 文件系统原生字节或完全不表示文本的二进制数据。

所以 `nsCString(value.data(), value.size())` 只复制字节，不会验证或转换 UTF-8。
变量名、函数名和接口文档应明确写出其语义，例如 `aUtf8`、`aBytes`、`aLatin1`。

## 4. UTF-8 与 UTF-16 转换

转换声明集中在 `xpcom/string/nsReadableUtils.h`，便捷临时类位于
`xpcom/string/nsString.h`。

### 4.1 API 选型

| 需求 | 推荐 API | 目标行为 |
| --- | --- | --- |
| 表达式中临时 UTF-8 -> UTF-16 | `NS_ConvertUTF8toUTF16(source)` | 返回 `nsAutoString` 子类 |
| 表达式中临时 UTF-16 -> UTF-8 | `NS_ConvertUTF16toUTF8(source)` | 返回 `nsAutoCString` 子类 |
| 覆盖目标 UTF-16 | `CopyUTF8toUTF16(source, dest)` | 清空旧内容后写入 |
| 追加到目标 UTF-16 | `AppendUTF8toUTF16(source, dest)` | 保留旧内容后追加 |
| 覆盖目标 UTF-8 | `CopyUTF16toUTF8(source, dest)` | 清空旧内容后写入 |
| 追加到目标 UTF-8 | `AppendUTF16toUTF8(source, dest)` | 保留旧内容后追加 |
| 新分配 `char*` | `ToNewUTF8String(source)` | 调用者必须 `free()` |
| 新分配 `char16_t*` | `UTF8ToNewUnicode(source)` | 调用者必须 `free()` |

典型代码：

```cpp
#include "nsString.h"

void ConsumeUTF16(const nsAString& aText);
void ConsumeUTF8(const nsACString& aText);

void ConvertExamples(const nsACString& aUtf8, const nsAString& aUtf16) {
  // 临时对象活到整个函数调用表达式结束。
  ConsumeUTF16(NS_ConvertUTF8toUTF16(aUtf8));
  ConsumeUTF8(NS_ConvertUTF16toUTF8(aUtf16));

  nsAutoString utf16;
  CopyUTF8toUTF16(aUtf8, utf16);

  nsAutoCString utf8("prefix:");
  AppendUTF16toUTF8(aUtf16, utf8);
}
```

`.get()` 只应在被调用函数需要 NUL 结尾指针时使用：

```cpp
void ConsumeBuffer(const char* aUtf8);

ConsumeBuffer(NS_ConvertUTF16toUTF8(aUtf16).get());  // 本次调用期间有效
```

不要保存上述临时对象的 `.get()` 结果；分号后临时对象已销毁。对具名字符串而言，
修改、重新分配或销毁字符串也会使已取得的指针失效。

### 4.2 非法输入与内存失败不是同一种错误

UTF 转换的内容错误策略在源码中是明确的：

- UTF-8 -> UTF-16：非法 UTF-8 字节序列替换为 `U+FFFD`，见
  `xpcom/string/nsReadableUtils.h:66`。
- UTF-16 -> UTF-8：孤立代理项替换为 `U+FFFD` 的 UTF-8 编码，见
  `xpcom/string/nsReadableUtils.h:130`。

因此这些常用转换是“替换式解码”，不会因为输入格式错误返回 `false`。带
`mozilla::fallible` 的重载只把分配失败暴露为 `false`：

```cpp
nsresult ConvertFallibly(const nsACString& aUtf8, nsAString& aDest) {
  if (!CopyUTF8toUTF16(aUtf8, aDest, mozilla::fallible)) {
    return NS_ERROR_OUT_OF_MEMORY;
  }
  return NS_OK;
}
```

不带 `mozilla::fallible` 的重载采用 Gecko 默认的不可失败分配策略，内存不足时调用
`AllocFailed()`，而不是返回错误。

若业务必须拒绝非法 UTF-8，而不是替换它，应使用
`mozilla::Encoding::DecodeWithoutBOMHandlingAndWithoutReplacement()` 或先用
`mozilla::IsUtf8()` 验证，不能依靠 `CopyUTF8toUTF16()` 做严格校验。

### 4.3 底层调用链

以 `NS_ConvertUTF8toUTF16` 为例：

```text
NS_ConvertUTF8toUTF16 构造函数
  -> AppendUTF8toUTF16
  -> nsstring_fallible_append_utf8_impl (C ABI)
  -> nsAString::fallible_append_utf8_impl (Rust)
  -> encoding_rs::mem::convert_utf8_to_utf16
  -> BulkWrite 直接写入目标字符串缓冲区
```

反方向使用 `nscstring_fallible_append_utf16_to_utf8_impl` 和
`encoding_rs::mem::convert_utf16_to_utf8`。Rust 实现在
`xpcom/rust/nsstring/src/conversions.rs:230` 与
`xpcom/rust/nsstring/src/conversions.rs:339` 附近。

这里有三个值得注意的实现细节：

- `Copy*` 把保留长度传为 0，`Append*` 传入目标当前长度；两者共用核心转换逻辑。
- 转换先计算最坏输出容量，再通过 `BulkWrite` 直接写目标，避免中间字符串。
- 长 ASCII/Basic Latin 前缀和 `nsAutoString` 的内联容量有专门快路径；这些优化不改变
  上层 API 的编码语义。

## 5. 名称为 ASCII、实际为 Latin-1 的历史 API

`CopyASCIItoUTF16`、`AppendASCIItoUTF16`、`NS_ConvertASCIItoUTF16` 名称源自历史，
实现实际把每个**无符号字节值**零扩展成同值 Unicode 标量，即 Latin-1 语义；它们
不是 Windows-1252 解码器。源码注释见 `xpcom/string/nsReadableUtils.h:96`。

反方向的 `LossyCopyUTF16toASCII`、`LossyAppendUTF16toASCII`、
`NS_LossyConvertUTF16toASCII` 实际是危险的 UTF-16 -> Latin-1 窄化：

- 只应在已证明所有输入都不超过 `U+00FF` 时使用；
- 对超出范围的代码点，release 构建会产生不可依赖的垃圾结果；
- 这不是把“不可表示字符替换为 `?`”的通用转换；
- 只为打印文本而转窄时，应转成 UTF-8。

另外还有 `CopyLatin1toUTF8`、`AppendLatin1toUTF8`、
`LossyCopyUTF8toLatin1` 等 8 位到 8 位的显式转换。只要输入可能是 Windows-1252、
网页响应体或其他传统编码，就应改用下一节的 `mozilla::Encoding`。

特别注意：

- `ToNewCString(const nsAString&)` 走有损 Latin-1 窄化，**不是 UTF-8**；
- `ToNewUTF8String(const nsAString&)` 才是 UTF-16 -> UTF-8；
- `ToNewUnicode(const nsACString&)` 是 Latin-1 -> UTF-16；
- `UTF8ToNewUnicode(const nsACString&)` 才是 UTF-8 -> UTF-16。

## 6. 任意网页编码：`mozilla::Encoding`

Shift_JIS、GBK、Big5、Windows-1252 等编码由 `mozilla::Encoding` 处理。该 C++ API
定义在 `intl/Encoding.h`，底层连接 Rust `encoding_rs`；旧式
`nsICharsetConversion` 不应作为 Firefox 130 的主转换方案。

常用入口如下：

- 编码在编译期已知：使用 `UTF_8_ENCODING`、`SHIFT_JIS_ENCODING` 等静态对象。
- 编码来自协议标签：使用 `Encoding::ForLabel()`；无法识别时返回 `nullptr`。
- 不允许 replacement 编码标签：使用 `ForLabelNoReplacement()`。
- 需要 BOM 探测：使用 `ForBOM()` 或带 BOM 策略的 `Decode()`。
- 输入是完整缓冲区：使用分配型 `Decode*()` / `Encode()`。
- 输入分片到达：使用 `NewDecoder*()` / `NewEncoder()` 保存跨片状态，不能逐片调用
  完整缓冲区 API。

BOM 策略必须显式选择：

| API | BOM 行为 |
| --- | --- |
| `Decode()` / `NewDecoder()` | 探测 BOM，实际编码可能切换为 UTF-8/UTF-16LE/UTF-16BE |
| `DecodeWithBOMRemoval()` | 按已选编码解码，并移除其 BOM |
| `DecodeWithoutBOMHandling()` | 不探测也不移除，BOM 按普通输入内容处理 |
| `NS_ConvertUTF8toUTF16()` | 只是 UTF-8 内容转换，不承担协议级 BOM 探测 |

示例：把一整块指定传统编码的字节严格解码为 UTF-16。

```cpp
#include "mozilla/Encoding.h"
#include "nsString.h"

nsresult DecodeStrict(const nsACString& aBytes, const nsACString& aLabel,
                      nsAString& aOut) {
  const mozilla::Encoding* encoding =
      mozilla::Encoding::ForLabelNoReplacement(aLabel);
  if (!encoding) {
    return NS_ERROR_UCONV_NOCONV;
  }

  mozilla::Span<const uint8_t> bytes = aBytes;
  return encoding->DecodeWithoutBOMHandlingAndWithoutReplacement(bytes, aOut);
}
```

严格版本遇到非法字节序列返回 `NS_ERROR_UDEC_ILLEGALINPUT`。允许替换的解码版本会
输出 `U+FFFD`，并用成功码 `NS_OK_HAD_REPLACEMENTS` 告知发生过替换；调用者若关心
数据质量，不能只用 `NS_SUCCEEDED(rv)` 后丢弃该信息。

`Decode*()` 可直接输出：

- `nsAString`：UTF-16；
- `nsACString`：UTF-8。

`Encode()` 接收 UTF-16 或有效 UTF-8，并输出目标编码字节。不可映射字符的便捷完整
缓冲区版本按 Encoding Standard 生成十进制数字字符引用，并以
`NS_OK_HAD_REPLACEMENTS` 报告。返回 tuple 的第二项是实际使用的 output encoding；
例如部分编码按规范以 UTF-8 作为输出编码，不能永远假设它等同于最初选择的对象。

## 7. 字面量、原始指针与标准库互操作

### 7.1 字面量

Firefox 130 推荐用户定义字面量：

```cpp
const nsLiteralCString asciiOrUtf8 = "content-type"_ns;  // 8 位字节
const nsLiteralString utf16 = u"界面文本"_ns;             // UTF-16
```

`operator""_ns` 定义在 `xpcom/string/nsLiteralString.h:23`。字面量的长度在编译期
已知，底层存储具有静态生命周期。旧初稿列出的 `NS_LITERAL_CSTRING`、
`NS_NAMED_LITERAL_CSTRING`、`NS_LITERAL_STRING`、`NS_NAMED_LITERAL_STRING` 不应作为
本版本新代码的推荐写法。

### 7.2 `char*` / `char16_t*`

```cpp
const char* utf8Buffer = GetUTF8();
nsDependentCString utf8View(utf8Buffer);  // 不复制；要求 NUL 结尾
nsAutoString text = NS_ConvertUTF8toUTF16(utf8View);

const char16_t* utf16Buffer = GetUTF16();
nsDependentString utf16View(utf16Buffer);  // 不复制；要求 NUL 结尾
nsAutoCString utf8 = NS_ConvertUTF16toUTF8(utf16View);
```

如果源数据给出了显式长度但不保证末尾 NUL，应使用 `Substring(ptr, len)` 或
`nsDependent[C]Substring`，不能构造 `nsDependent[C]String`。后者在
`xpcom/string/nsTString.h` 的 `AssertValidDependentString()` 中断言结尾条件。

### 7.3 `std::string` / `std::u16string`

同宽转换只是复制代码单元，不做转码：

```cpp
std::string ToStdBytes(const nsACString& aBytes) {
  return std::string(aBytes.Data(), aBytes.Length());
}

std::u16string ToStdUTF16(const nsAString& aText) {
  return std::u16string(aText.Data(), aText.Length());
}

nsCString FromStdBytes(const std::string& aBytes) {
  return nsCString(aBytes.data(), aBytes.size());
}

nsString FromStdUTF16(const std::u16string& aText) {
  return nsString(aText.data(), aText.size());
}
```

显式传长度可保留内嵌 NUL；只传 C 指针的构造或 `.get()` 消费方通常会在第一个 NUL
处停止。

`wchar_t` 的宽度跨平台不同。Windows 下 `nsString::getW()` 提供受平台保护的
`const wchar_t*` 视图；不要把 `char16_t*` 到 `wchar_t*` 的 `reinterpret_cast` 写成
跨平台代码。

## 8. 文件路径不是普通文本转换问题

`ipc/chromium/src/base/file_path.h` 中的 `FilePath::StringType` 在 POSIX 是
`std::string`，在 Windows 是 UTF-16 `std::wstring`。正确原则是尽量把
`FilePath` 保持为平台原生路径，在系统调用边界使用 `value().c_str()`，不要为了统一
接口先强制转成 `char*`。

- Windows 确需逻辑 UTF-8 时，可使用 `base::SysWideToUTF8()`；反向用
  `base::SysUTF8ToWide()`。
- POSIX 路径本质上可以是任意非 NUL 字节，不能普遍假设有效 UTF-8；Firefox 自身的
  上层约定可能比 OS 更严格，必须看具体 API 契约。
- Gecko 文件接口优先使用 `nsIFile` 和 `mozilla::PathString`；后者按
  `mozilla::filesystem::Path::value_type` 选择平台代码单元，定义见
  `xpcom/io/nsIFile.idl:17`。

## 9. 常见陷阱与审查清单

1. **把 `nsCString` 当作默认 UTF-8**：错误。先追踪生产者和消费者的编码契约。
2. **直接跨宽度 `Assign`/`Append`**：8 位和 16 位 API 类型隔离；使用明确转换函数。
3. **用 `Lossy*ASCII*` 处理任意 Unicode**：错误，超出 Latin-1 的结果不可依赖。
4. **把 `CopyASCIItoUTF16` 当 Windows-1252**：错误，它是逐字节 Latin-1 扩展。
5. **把 `.Length()` 当用户可见字符数**：错误，它返回代码单元数。
6. **长期保存 `.get()`**：字符串修改、销毁或临时对象表达式结束后指针可能失效。
7. **忽略内嵌 NUL**：字符串对象有显式长度，但许多 C API 没有。
8. **让 dependent view 活得比源缓冲区久**：会产生悬空引用。
9. **对流的每个分片分别 Decode**：多字节序列可能跨片，应使用状态化 `Decoder`。
10. **忽略 `NS_OK_HAD_REPLACEMENTS`**：它是成功码，但表示输入或输出发生数据替换。

## 10. 初稿主要勘误

| 初稿说法 | Firefox 130 源码结论 |
| --- | --- |
| `nsCString` 用于“非 Unicode/ASCII”，或默认是 UTF-8 | 它只是 8 位字节容器；编码由上下文决定 |
| 16 位字符串“永远是有效 UTF-16” | 它按 UTF-16 解释，但可以包含孤立代理项 |
| `nsCAutoString`、`nsCDependentString` 是当前主名称 | 当前公开别名是 `nsAutoCString`、`nsDependentCString` |
| `nsString` 总是堆分配、独占数据 | 它保证 NUL 结尾，但可使用多种动态缓冲区模式 |
| `nsAutoString` 可内联 64 个字符 | 数组 64 个代码单元，需留一个 NUL，默认容量为 63 |
| `LossyCopyToString` / `CopyToBuffer` 是宽窄转换主 API | 本版本使用 `NS_Convert*`、`Copy*`、`Append*` 自由函数 |
| 可直接 `nsCString.Append(nsString)` | 宽度不同，必须显式说明 UTF-8、Latin-1 或其他编码转换 |
| `InitWithCString` 可把 `char*` 转为 `nsString` | 该示例 API 不属于这些字符串类；应按源编码显式转换 |
| `nsDependentString` 可包装 `char*` | 宽版本需要 `char16_t*`；`char*` 对应 `nsDependentCString` |
| `NS_LITERAL_*` 宏是首选 | Firefox 130 新代码首选 `"..."_ns` 与 `u"..."_ns` |
| 传统编码主要通过 `nsICharsetConversion` | Firefox 130 主入口是 `mozilla::Encoding`/`encoding_rs` |
| Windows 上手工 `reinterpret_cast<wchar_t*>` | 使用平台限定的 `getW()` 或相应平台转换 API |

## 11. 快速决策表

| 已有数据 | 目标 | 选择 |
| --- | --- | --- |
| 已知有效或可替换非法序列的 UTF-8 字节 | UTF-16 | `CopyUTF8toUTF16` / `NS_ConvertUTF8toUTF16` |
| 可能含孤立代理项的 UTF-16 | 有效 UTF-8 | `CopyUTF16toUTF8` / `NS_ConvertUTF16toUTF8` |
| 必须拒绝非法 UTF-8 | UTF-16 或 UTF-8 | `Encoding` 的 `...WithoutReplacement` 解码 |
| 真正 Latin-1 字节 | UTF-16 | `CopyASCIItoUTF16`，并在代码中注明 Latin-1 语义 |
| 已证明位于 Latin-1 范围的 UTF-16 | Latin-1 | `LossyCopyUTF16toASCII`，谨慎使用 |
| Windows-1252/GBK/Shift_JIS 等字节 | Unicode | `mozilla::Encoding` |
| 不拥有且已 NUL 结尾的同宽缓冲区 | 字符串只读视图 | `nsDependent[C]String` |
| 不拥有、只有指针和长度的同宽缓冲区 | 区间只读视图 | `Substring()` / `nsDependent[C]Substring` |
| `std::string` 与 `nsCString` | 保持相同字节 | 显式指针加长度复制，不发生转码 |
| 平台路径 | OS API | 保持 `FilePath` / `PathString` 原生表示 |
