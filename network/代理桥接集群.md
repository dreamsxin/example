## 设计方案集

以下针对“代理桥接集群”场景，分别给出五种可行的完整设计方案。  
所有方案均满足核心要求：  
- 客户端无法直连上游 SOCKS5 代理，必须通过桥节点转发。  
- 桥节点仅能连接已授权的代理列表，且通过代理认证进行最终授权。  
- 客户端能够自动选择负载最低、延时最小的桥节点。  
- **注册中心（etcd）不直接暴露给客户端**，避免安全风险。

---

### 方案一：双注册中心（etcd + 服务发现组件）

#### 架构图
```
                    ┌─────────────────┐
                    │   etcd 集群      │  (存储代理池配置)
                    └────────┬────────┘
                             │ 监听代理列表变化
                    ┌────────▼────────┐
                    │   桥节点集群     │
                    └────────┬────────┘
                             │ 向服务发现组件注册/上报负载
                    ┌────────▼────────┐
                    │ Consul/Nacos    │  (服务发现与健康检查)
                    └────────┬────────┘
                             │ 查询桥列表+负载
                    ┌────────▼────────┐
                    │     客户端       │
                    └─────────────────┘
```

#### 组件说明
1. **etcd 集群**  
   - 存储代理池信息：代理 ID、地址、认证凭据（可加密）、状态。  
   - 仅桥节点可访问，通过 TLS 和 RBAC 控制权限。  
   - 客户端完全不可达。  

2. **服务发现组件（Consul / Nacos）**  
   - 桥节点启动时注册自身服务（IP、端口、健康检查接口）。  
   - 桥节点周期性上报负载指标（CPU、内存、连接数）。  
   - 客户端通过该组件查询桥列表及实时负载，但不暴露 etcd。  

3. **桥节点**  
   - 从 etcd 加载代理池并监听变化。  
   - 向服务发现组件注册并上报负载。  
   - 处理客户端连接，验证代理请求并转发。  

4. **客户端**  
   - 从服务发现组件获取桥列表。  
   - 对每个桥进行测速（如 TCP 握手延迟）。  
   - 结合负载与延迟选择最优桥，直连并认证。  

#### 工作流程
1. 管理员在 etcd 中配置代理池。  
2. 桥节点启动，从 etcd 拉取代理列表，并保持 Watch。  
3. 桥节点向 Consul 注册，并定期上报健康状态与负载。  
4. 客户端启动，查询 Consul 获取桥节点列表及负载。  
5. 客户端测速，计算 `Score = β*(1-Load) + γ*(1-LatencyScore)`，选择最优桥。  
6. 客户端连接桥，认证时提供代理标识和凭据。  
7. 桥验证代理标识在白名单中，使用客户端提供的凭据连接上游代理，若成功则建立隧道。  

#### 安全设计
- **etcd 隔离**：仅内网可达，使用 mTLS 和 RBAC。  
- **服务发现组件安全**：如果暴露给客户端，需启用 ACL 或至少限制为只读查询；若客户端不可信，建议在服务发现组件前面再加一层 API 网关进行鉴权。  
- **客户端与桥之间**：TLS 加密，防止凭据泄露。  

#### 优缺点
- **优点**：职责分离，etcd 专注配置，服务发现组件专注健康检查和动态负载。  
- **缺点**：需要维护两套系统，部署复杂度较高；需保证两者数据的一致性。

### 方案二：单一 etcd + 只读 API 网关

#### 架构图
```
                    ┌─────────────────┐
                    │   etcd 集群      │
                    └───┬─────────┬───┘
             监听/读写  │         │ 只读查询
                    ┌──▼──┐   ┌──▼──────────┐
                    │ 桥   │   │ 只读 API 网关│ (鉴权、限流)
                    └──┬──┘   └──┬──────────┘
                       │注册/负载│ 查询桥列表
                    ┌──▼─────────▼──┐
                    │     客户端      │
                    └────────────────┘
```

#### 组件说明
1. **etcd 集群**  
   - 同时存储代理池和桥节点信息（`/proxies/`、`/bridges/`）。  
   - 仅允许桥节点和 API 网关访问，通过 mTLS 和 RBAC 严格限制。  

2. **只读 API 网关**  
   - 对外提供简单的 HTTP API，如 `GET /bridges`。  
   - 从 etcd 读取桥列表及负载，返回给客户端。  
   - 实现客户端认证（Token）、限流、日志。  

3. **桥节点**  
   - 向 etcd 注册自身并周期性更新负载（使用租约保活）。  
   - 监听 `/proxies/` 变化，更新本地代理列表。  

4. **客户端**  
   - 仅与 API 网关交互，获取桥列表。  
   - 可自行测速或由 API 网关根据客户端 IP 进行预筛选。  

#### 工作流程
1. 桥启动，向 etcd 写入自身信息并定时刷新。  
2. 客户端请求 API 网关获取桥列表。  
3. API 网关验证客户端 Token，从 etcd 读取活跃桥及负载，返回给客户端。  
4. 客户端对返回的桥进行测速，选择最优桥连接。  
5. 桥处理认证与转发（同方案一）。  

#### 安全设计
- etcd 完全内网，不直接暴露。  
- API 网关是唯一入口，强制鉴权。  
- 网关只提供只读操作，无法修改配置。  

#### 优缺点
- **优点**：只维护一个注册中心，组件更少；通过 API 网关隔离，安全性好。  
- **缺点**：API 网关可能成为性能瓶颈，但可通过水平扩展解决；客户端仍需自行测速，逻辑稍复杂。

### 方案三：引导服务器 + etcd（推荐）

#### 架构图
```
                    ┌─────────────────┐
                    │   etcd 集群      │
                    └───┬─────────┬───┘
             读写/监听  │         │ 读桥列表+负载
                    ┌──▼──┐   ┌──▼──────────┐
                    │ 桥   │   │ 引导服务器   │ (调度决策)
                    └──┬──┘   └──┬──────────┘
                       │注册/负载│ 返回最优桥
                    ┌──▼─────────▼──┐
                    │     客户端      │
                    └────────────────┘
```

#### 组件说明
1. **etcd 集群**  
   - 存储代理池和桥节点信息，仅供内网组件访问。  

2. **引导服务器**  
   - 无状态服务，可水平扩展。  
   - 对外提供 `GET /get-best-bridge` API。  
   - 从 etcd 获取桥实时负载，结合客户端 IP（可选）计算最优桥并返回。  
   - 实现鉴权、限流、日志。  

3. **桥节点**  
   - 向 etcd 注册并上报负载，监听代理列表变化。  

4. **客户端**  
   - 只需请求引导服务器一次，获得一个最佳桥地址，直连该桥。  
   - 无需自己维护桥列表或测速。  

#### 工作流程
1. 桥节点启动，注册到 etcd。  
2. 客户端向引导服务器发起请求（携带 Token）。  
3. 引导服务器验证身份，读取 etcd 中桥负载，使用调度算法（如加权轮询、最小负载、地理就近）选择最优桥。  
4. 引导服务器返回桥地址给客户端。  
5. 客户端连接该桥，认证并请求代理。  
6. 若桥故障，客户端重新请求引导服务器获取新桥。  

#### 安全设计
- etcd 完全隔离，客户端不感知。  
- 引导服务器集中鉴权，可集成 OAuth2、API Key 等。  
- 返回的桥地址可以加密或使用一次性令牌，防止重放。  

#### 优缺点
- **优点**：客户端实现最简单；调度策略集中，易于优化；安全性高。  
- **缺点**：引导服务器是额外依赖，需要保证高可用；客户端不主动测速，可能错过微观网络差异，但引导服务器可根据客户端 IP 选择就近桥。

### 方案四：动态 DNS + 健康检查

#### 架构图
```
                    ┌─────────────────┐
                    │   etcd 集群      │ (仅代理池)
                    └────────┬────────┘
                             │ 监听
                    ┌────────▼────────┐
                    │   桥节点集群     │
                    └────────┬────────┘
                             │ 健康检查
                    ┌────────▼────────┐
                    │ 监控服务 + DNS 更新 │
                    └────────┬────────┘
                             │ 动态更新DNS记录
                    ┌────────▼────────┐
                    │    DNS 服务      │
                    └────────┬────────┘
                             │ 解析域名
                    ┌────────▼────────┐
                    │     客户端       │
                    └─────────────────┘
```

#### 组件说明
1. **etcd**：仅存储代理池配置，不参与客户端发现。  
2. **桥节点**：从 etcd 获取代理列表，对外提供代理服务。  
3. **监控服务**：周期性检查桥节点健康状态和负载，通过 API 更新 DNS 记录（如增加/删除 IP，调整权重）。  
4. **DNS 服务**：可使用 Cloudflare、Route53 或自建 CoreDNS + etcd。  
5. **客户端**：直接使用域名作为代理地址，DNS 轮询返回多个桥 IP。  

#### 工作流程
1. 桥节点启动，监控服务检测到并将桥 IP 加入 DNS 记录。  
2. 监控服务持续检查桥负载，动态调整 DNS 权重或移除不健康节点。  
3. 客户端配置代理域名，如 `bridge.example.com:1080`。  
4. DNS 解析返回多个桥 IP，客户端默认使用第一个（或随机）。  
5. 桥节点处理认证与转发（同前）。  

#### 安全设计
- 客户端只接触 DNS，无法获取 etcd 或代理池信息。  
- 需要保护 DNS 管理 API，防止恶意篡改。  

#### 优缺点
- **优点**：客户端完全透明，无需任何修改。  
- **缺点**：DNS 缓存导致故障转移慢；无法实时感知负载，只能粗粒度；无法做到精确的“最低延迟”选择。

### 方案五：客户端静态桥列表 + 测速（无注册中心）

#### 架构图
```
                    ┌─────────────────┐
                    │   etcd 集群      │ (代理池)
                    └────────┬────────┘
                             │
                    ┌────────▼────────┐
                    │   桥节点集群     │
                    └────────┬────────┘
                             ▲
                             │ 客户端内置桥IP列表，自行测速
                    ┌────────┴────────┐
                    │     客户端       │
                    └─────────────────┘
```

#### 组件说明
1. **etcd**：仅管理代理池，桥节点从中获取代理配置。  
2. **桥节点**：固定部署，地址预先配置在客户端中。  
3. **客户端**：内置一组桥节点地址（IP 或域名），启动时对每个桥测速，选择延迟最低的桥。  
4. **无服务发现组件**：桥地址更新需要手动更新客户端配置。  

#### 工作流程
1. 客户端从本地配置读取桥列表。  
2. 对每个桥发起测速探测（TCP 握手、HTTP 请求等）。  
3. 选择延迟最低的桥建立连接。  
4. 桥处理认证与转发。  

#### 安全设计
- 无注册中心暴露，客户端只需知道桥地址。  
- 桥地址可能泄露，需确保桥本身有强认证。  

#### 优缺点
- **优点**：架构最简单，无额外依赖。  
- **缺点**：桥地址变更或扩容时需更新所有客户端；无法动态感知桥负载，只能依据延迟，可能选择高负载桥。

## 方案对比总结

| 方案 | 客户端逻辑复杂度 | 实时负载感知 | 故障转移速度 | 安全性 | 部署复杂度 | 推荐场景 |
|------|------------------|--------------|--------------|--------|------------|----------|
| 双注册中心 | 中（需测速+选择） | 高 | 快 | 较高 | 高 | 大型生产环境，需灵活调度 |
| 单一 etcd + API 网关 | 中（需测速+选择） | 高 | 快 | 高 | 中 | 中等规模，希望减少组件 |
| **引导服务器 + etcd** | **极低（一次请求）** | **高** | **快** | **高** | **中** | **多数生产环境首选** |
| 动态 DNS | 无 | 低 | 慢 | 中 | 低 | 极简个人或小规模 |
| 静态桥列表 | 低（仅测速） | 无 | 中 | 中 | 极低 | 固定环境、桥很少 |

**最终推荐**：方案三（引导服务器 + etcd）在安全性、实时性、客户端易用性之间取得了最佳平衡，是最适合你需求的设计。

## 方案三完整设计：引导服务器 + etcd

### 1. 系统概述

本方案旨在构建一个安全、高效的代理桥接集群，用于解决客户端无法直连上游 SOCKS5 代理的问题。系统通过桥节点中转流量，并引入引导服务器作为客户端与内部注册中心（etcd）之间的安全网关，实现客户端自动选择负载最低、延时最小的桥节点。系统核心目标：

- 桥节点仅连接预授权的上游 SOCKS5 代理，并通过代理认证进行最终授权。
- 客户端无需直接访问 etcd，仅通过引导服务器获取最优桥节点地址。
- 支持动态扩展、故障自动转移和细粒度的调度策略。

### 2. 总体架构

```
┌─────────────────────────────────────────────────────────────┐
│                        客户端 (用户)                         │
│  ┌──────────────────────────────────────────────────────┐  │
│  │ 1. 请求引导服务器获取最佳桥节点                         │  │
│  │ 2. 直连桥节点，认证并转发流量                          │  │
│  └──────────────────────────────────────────────────────┘  │
└────────────────────────┬───────────────────────────────────┘
                         │ HTTPS (Token认证)
                         ▼
               ┌─────────────────┐
               │   引导服务器集群  │  (无状态，可水平扩展)
               │  - 鉴权          │
               │  - 从etcd读取桥负载│
               │  - 调度算法       │
               └────────┬────────┘
                         │ 读写(仅读桥信息)
                         ▼
               ┌─────────────────┐
               │   etcd 集群      │
               │  - 代理池配置    │
               │  - 桥节点注册表  │
               │  - 负载指标      │
               └────────┬────────┘
                         │ 读写/监听
                         ▼
               ┌─────────────────┐
               │   桥节点集群      │
               │  - 注册/心跳      │
               │  - 上报负载       │
               │  - 监听代理列表   │
               │  - 代理转发       │
               └────────┬────────┘
                         │ 连接上游代理
                         ▼
               ┌─────────────────┐
               │ 上游SOCKS5代理池  │
               └─────────────────┘
```

- **etcd 集群**：仅内网可达，不暴露给客户端。存储代理池配置和桥节点注册信息（包括实时负载）。使用 mTLS 和 RBAC 严格控制访问权限。
- **引导服务器（Bootstrap）**：对外提供 HTTPS API，接收客户端请求，从 etcd 读取桥节点负载，执行调度算法，返回最优桥节点地址。引导服务器本身无状态，可多实例部署，通过负载均衡或 DNS 轮询对外提供服务。
- **桥节点**：数据面组件。启动时向 etcd 注册自身信息，周期性上报负载指标，同时监听代理池配置变化。负责处理客户端连接，验证客户端请求的代理是否在白名单内，并使用对应凭据连接上游代理进行转发。
- **客户端**：仅需知道引导服务器地址，通过 HTTPS 携带 Token 请求获取最佳桥节点，然后直连该桥节点进行 SOCKS5 认证和通信。

### 3. 各组件详细设计

#### 3.1 etcd 集群

##### 3.1.1 数据模型

etcd 使用层级键值存储，建议设计如下：

```
/proxies/
    {proxy_id}/
        address: "1.2.3.4:1080"            # 上游代理地址
        username: "user123"                # 上游代理用户名（可加密）
        password: "encrypted_password"     # 加密后的密码，或引用KMS
        status: "active"                   # active/disabled
        tags: ["US", "high-anonymity"]     # 可选标签，用于调度
        max_connections: 1000              # 该代理允许的最大连接数
        created_at: "..."
        updated_at: "..."
/bridges/
    {bridge_id}/
        ip: "10.0.0.5"
        port: 1080                         # SOCKS5监听端口
        hostname: "bridge-1"
        status: "online"                   # online/offline
        last_heartbeat: "2025-01-01T00:00:00Z"
        load:
            cpu: 0.35                      # 0~1
            memory: 0.60                   # 0~1
            connections: 120               # 当前活跃连接数
            max_connections: 500           # 最大连接数
            net_in_bps: 1024000
            net_out_bps: 2048000
            updated_at: "..."
        geo: {latitude: 35.6, longitude: 139.7}   # 可选地理位置
        version: "1.2.3"                   # 桥节点版本
```

- **代理池配置**：由管理员维护，可在 etcd 中直接操作或通过管理 API。密码应加密存储，桥节点读取后解密。
- **桥节点注册表**：桥节点使用租约（Lease）写入自身信息，并定期刷新心跳和负载。租约过期后键自动删除，实现故障检测。

##### 3.1.2 权限控制

- etcd 启用 **mTLS**：所有客户端（桥节点、引导服务器）必须持有由内部 CA 签发的证书才能连接。
- 使用 **RBAC** 角色：
  - `bridge-role`：允许读写 `/bridges/{bridge_id}`（自身键）、读取 `/proxies/`。
  - `bootstrap-role`：允许读取 `/bridges/`、读取 `/proxies/`（可选，用于过滤）。
  - `admin-role`：完全控制。
- 客户端完全无法访问 etcd。

#### 3.2 引导服务器

##### 3.2.1 API 设计

对外提供 RESTful HTTPS API：

- **`GET /v1/bootstrap/best-bridge`**  
  请求参数（Header）：  
  - `Authorization: Bearer <client_token>`  
  可选 Query 参数：  
  - `client_ip`（可选，客户端公网 IP，用于地理就近选择，也可由服务器从连接中获取）  
  - `preferred_region`（可选，用户偏好地区）  
  - `proxy_id`（可选，若客户端已指定目标代理，引导可返回能访问该代理的桥节点）  

  响应示例（200 OK）：
  ```json
  {
    "bridge": {
      "id": "bridge-01",
      "address": "203.0.113.10:1080",
      "expires_at": "2025-01-01T00:05:00Z"
    }
  }
  ```
  或返回多个桥（备用）：
  ```json
  {
    "bridges": [
      {"id": "bridge-01", "address": "203.0.113.10:1080"},
      {"id": "bridge-02", "address": "203.0.113.11:1080"}
    ]
  }
  ```

- **`GET /healthz`**：健康检查，返回 200。

##### 3.2.2 鉴权与安全

- 客户端需预先申请 **API Token**，引导服务器验证 Token 有效性（可对接内部用户系统或使用 JWT 签名）。
- Token 可包含权限范围（如允许使用的代理组、地域等）。
- 引导服务器对请求进行限流（如每 Token 每分钟最大请求数），防止滥用。
- 所有通信必须使用 HTTPS（TLS 1.2+），建议启用 HSTS。

##### 3.2.3 调度算法

引导服务器从 etcd 获取所有在线桥节点的负载信息，结合客户端信息（如 IP 地理位置）计算每个桥的得分，选择得分最高的桥返回。

**得分计算参考公式：**

```
Score = α * (1 - LoadScore) + β * (1 - LatencyScore) + γ * GeoScore
```

- **LoadScore**：综合负载指标归一化后的值（0~1，1表示满载）。  
  可由桥节点上报的 cpu、memory、connections、net 加权计算：  
  `LoadScore = w1*cpu + w2*memory + w3*(connections/max_connections) + w4*net_ratio`  
  权重可根据业务调整，例如 `w1=0.3, w2=0.2, w3=0.4, w4=0.1`。

- **LatencyScore**：桥节点到客户端的预估延迟（0~1）。由于客户端不会主动测速，引导服务器可采用以下方式估算：
  - 根据客户端 IP 与桥节点 IP 的地理位置距离（GeoIP 数据库）计算大致的 RTT 值。
  - 维护一个历史延迟矩阵：桥节点定期测量到各大区域（或代表性 IP）的延迟并上报，引导服务器查询客户端所在区域对应的延迟。
  - 简单场景可忽略该项，仅考虑负载，或设置 `LatencyScore = 0`。

- **GeoScore**：地理匹配度（0~1）。如果客户端有地域偏好或需要选择同区域桥，可计算客户端与桥节点的距离映射为得分。距离越近，GeoScore 越高。

- **α, β, γ** 为权重，默认 `α=0.5, β=0.3, γ=0.2`，可根据策略调整。引导服务器可动态调整权重（如高峰期更重视负载）。

**选择策略**：  
- 排除状态非 `online` 或租约已过期的桥。  
- 若客户端指定了 `proxy_id`，确保该桥已加载该代理（桥节点可在上报时附带其支持的代理列表摘要）。  
- 可选：对返回的桥地址附加一次性令牌或短期签名，防止客户端被引导至恶意桥（需桥验证）。

##### 3.2.4 引导服务器集群与高可用

- 引导服务器无状态，可部署多个实例，前端使用负载均衡器（如 Nginx、云 LB）或 DNS 轮询。
- 每个实例均能独立从 etcd 读取数据并响应请求。
- 若某实例故障，负载均衡自动剔除。

##### 3.2.5 缓存与性能优化

- 引导服务器可使用本地缓存（如 LRU）存储桥列表和负载，减少 etcd 读取压力，缓存 TTL 如 2~5 秒。
- 调度计算复杂度低，单实例可处理数千 QPS，水平扩展容易。

#### 3.3 桥节点

##### 3.3.1 功能模块

- **注册与心跳**：启动时生成唯一 `bridge_id`，向 etcd 写入 `/bridges/{bridge_id}` 并创建租约（TTL 如 10 秒），周期性续租并更新心跳和负载信息。
- **代理池管理**：监听 etcd 中 `/proxies/` 的前缀变化，在本地内存维护代理列表（地址、凭据）。当代理配置变更时动态更新。
- **客户端接入**：监听 SOCKS5 端口（如 1080），接受客户端连接。
- **认证与授权**：
  - 客户端在 SOCKS5 认证阶段提交用户名和密码。
  - 用户名格式约定：`proxy_id:username`（或仅 `proxy_id` 且密码为代理密码，但建议包含代理用户名）。
  - 桥节点解析 `proxy_id`，检查其是否存在于本地代理列表。若不存在，拒绝连接。
  - 使用解析出的代理用户名和密码（或本地代理列表中该代理的默认凭据）连接上游代理。如果连接成功，则建立客户端到上游代理的隧道；否则拒绝客户端。
- **数据转发**：在客户端与上游代理之间进行双向复制。
- **负载监控**：采集本机 CPU、内存、活跃连接数、网络吞吐等指标，随心跳上报。

##### 3.3.2 与 etcd 交互

- 使用 etcd 客户端库（如 Go 的 etcd/clientv3），启用 mTLS。
- 使用 Watch 监听 `/proxies/` 变化。
- 使用租约（Lease）保持自身键存活，并在租约中附带负载信息（建议使用单独的键存储负载，避免频繁更新整个桥信息）。

##### 3.3.3 安全细节

- 客户端与桥节点之间建议使用 **SOCKS5 over TLS**（如 stunnel 或自定义 TLS 包装），防止用户名密码明文泄露。
- 桥节点与上游代理之间若支持 TLS，则启用；否则依赖内网安全或 VPN。
- 桥节点应限制最大连接数，防止资源耗尽。
- 所有日志不记录明文密码。

#### 3.4 客户端

##### 3.4.1 行为流程

1. **获取桥节点**：客户端启动或需要连接时，向引导服务器发送 HTTPS 请求（携带 Token），获取一个或多个桥节点地址。
2. **建立连接**：使用返回的地址连接桥节点的 SOCKS5 端口。
3. **认证**：按照约定的用户名格式提交 `proxy_id:proxy_username` 和代理密码。若仅需使用桥默认代理，可只填代理密码（需桥支持简化模式）。
4. **使用代理**：认证通过后，正常进行 SOCKS5 握手和后续数据传输。
5. **故障处理**：若连接断开或桥不可用，客户端可重新请求引导服务器获取新桥，或使用响应中提供的备用桥列表。

##### 3.4.2 客户端要求

- 支持配置引导服务器 URL 和 API Token。
- 支持标准 SOCKS5 协议，但可能需要自定义认证信息格式（一般代理客户端可自定义用户名密码）。
- 如果使用 TLS 包装，需要支持相应配置（如使用 stunnel 或内置 TLS 的定制客户端）。

### 4. 关键流程

#### 4.1 桥节点启动注册

1. 桥节点读取本地配置（包括 etcd 地址、证书、监听端口等）。
2. 连接 etcd，创建租约（TTL=10s）。
3. 向 `/bridges/{bridge_id}` 写入初始信息（IP、端口、状态=online）。
4. 启动心跳循环：每 5 秒更新心跳时间戳和负载信息，并续租。
5. 监听 `/proxies/` 前缀，加载代理列表。

#### 4.2 客户端获取桥节点并连接

1. 客户端向引导服务器发起 `GET /v1/bootstrap/best-bridge`。
2. 引导服务器验证 Token，从 etcd 读取所有在线桥的负载。
3. 计算得分，选出最优桥（可能返回多个，按得分排序）。
4. 返回桥地址给客户端。
5. 客户端连接该桥，进行 SOCKS5 认证。
6. 桥验证代理白名单和凭据，连接上游代理，建立隧道。

#### 4.3 桥节点故障处理

- etcd 中桥节点租约过期（未续租），`/bridges/{bridge_id}` 自动删除。
- 引导服务器读取时自动忽略该桥。
- 已连接该桥的客户端会检测到连接断开，重新请求引导服务器获取新桥。
- 若桥节点恢复，重新注册并上报负载。

### 5. 安全性设计汇总

| 通信链路 | 安全措施 |
|----------|----------|
| 客户端 ↔ 引导服务器 | HTTPS + Token 认证，可选 IP 白名单 |
| 客户端 ↔ 桥节点 | SOCKS5 over TLS（推荐），强认证 |
| 桥节点 ↔ etcd | mTLS + RBAC |
| 引导服务器 ↔ etcd | mTLS + RBAC（只读） |
| 桥节点 ↔ 上游代理 | 尽可能 TLS，或依赖内网隔离 |

- **etcd 不直接暴露**，仅内网可达，通过防火墙或 VPC 隔离。
- **代理凭据加密存储**，桥节点使用 KMS 或本地解密。
- **日志脱敏**，不记录密码等敏感信息。
- **定期轮换证书和 Token**。

### 6. 容错与高可用

- **etcd 集群**：至少 3 节点，跨可用区部署，保证强一致性和高可用。
- **引导服务器集群**：无状态，可部署多个实例，前端用负载均衡器（如 Nginx、云 LB）实现故障转移。若某个实例挂掉，负载均衡自动剔除。
- **桥节点**：无状态（代理列表从 etcd 动态获取），可随意扩缩容。故障时客户端自动切换。
- **上游代理**：若某代理故障，桥节点连接该代理会失败，可返回错误给客户端，客户端可重新请求引导并尝试其他代理（需客户端支持多代理配置）。

### 7. 监控与日志

- **桥节点**：上报 CPU、内存、连接数、网络流量、成功/失败认证次数等指标至监控系统（如 Prometheus）。
- **引导服务器**：记录请求日志（客户端 ID、请求时间、返回的桥 ID、耗时）、错误日志，监控 QPS、延迟。
- **etcd**：监控集群健康、Raft 状态、存储大小。
- **告警规则**：桥节点离线、负载过高、认证失败率骤增、引导服务器响应超时等。

### 8. 部署建议

- **etcd**：使用官方推荐方式部署，开启 mTLS，定期备份。
- **引导服务器**：可基于 Go、Python、Node.js 等开发，部署在容器平台（如 Kubernetes）或虚拟机，建议至少 2 个实例。
- **桥节点**：部署在全球多个地域以优化延迟，根据负载弹性伸缩。使用配置管理工具（如 Ansible）统一部署。
- **客户端分发**：提供配置文件或一键脚本，内置引导服务器地址和 Token。

### 9. 可选优化

- **智能缓存**：引导服务器缓存桥列表和负载 2~3 秒，降低 etcd 压力，同时保证实时性。
- **地理路由**：引导服务器使用 GeoIP 数据库，优先返回与客户端同区域的桥。
- **桥间隧道**：若上游代理只允许特定 IP 访问，桥节点之间可建立隧道，实现跨桥转发。
- **动态权重调整**：根据历史负载曲线预测高峰期，动态调整调度权重，实现更平滑的负载均衡。
- **一次性桥地址令牌**：引导服务器返回的桥地址可附带短期签名，桥验证后才接受连接，防止恶意客户端绕过引导直接连接桥。

### 10. 总结

方案三通过引导服务器作为安全屏障，将客户端与内部注册中心隔离，同时集中实现了智能调度，使得客户端能够自动选择最优桥节点。该方案在安全性、实时性、易用性和扩展性之间取得了良好平衡，适用于大多数生产环境。配合 etcd 的强大配置管理能力和桥节点的无状态设计，系统可轻松实现水平扩展和故障自愈。
