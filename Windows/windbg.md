# windbg 使用
### 📝 第一步：准备工作

在开始分析前，请确保你已备齐以下文件，这是成功分析的基础。

*   **Dump文件 (.dmp)**：程序崩溃时生成的“内存快照”。
*   **符号文件 (.pdb)**：连接机器码与源代码的“地图”，用于显示有意义的函数名和行号。
*   **二进制文件 (.exe, .dll)**：你的应用程序及所有依赖的二进制文件。

> **⚠️ 关键提醒**：`.exe`/`.dll`文件必须与其对应的`.pdb`文件**版本完全匹配**（通常是指编译时间戳一致），否则符号无法正确加载。

为方便操作，建议将所有文件（`.dmp`, `.pdb`, `.exe`, `.dll`）集中放在**同一个目录**下，例如 `D:\CrashAnalysis`。

### 🚀 第二步：打开Dump文件并配置路径

你可以通过图形界面或命令行两种方式打开Dump文件。

#### 方式一：图形界面操作
1.  启动 **WinDbg Preview**（推荐）或经典版 WinDbg。
2.  点击菜单栏的 **`File`** -> **`Open dump file`**，选择你的 `.dmp` 文件。

#### 方式二：命令行启动（推荐）
这种方式更直接，可以一次性配置好所有路径。
```bash
windbg -y "符号路径" -i "可执行文件路径" -z "Dump文件路径" -v
```
*   `-y`：指定符号文件路径。
*   `-i`：指定可执行文件路径。
*   `-z`：指定要打开的Dump文件。
*   `-v`：启用详细模式。

### ⚙️ 第三步：配置符号与可执行文件路径（最关键！）

打开Dump文件后，第一件事就是告诉WinDbg去哪里找符号和二进制文件。

在WinDbg底部的命令框中，依次输入以下命令：

1.  **设置符号路径 (`.sympath`)**：此命令告诉调试器符号文件的位置。
    ```text
    .sympath D:\CrashAnalysis; SRV*C:\Symbols*https://msdl.microsoft.com/download/symbols
    ```
    *   `D:\CrashAnalysis`：你存放`.pdb`文件的**本地目录**。
    *   `SRV*C:\Symbols*https://msdl.microsoft.com/download/symbols`：配置微软公共符号服务器。当需要系统DLL（如`ntdll.dll`）的符号时，WinDbg会从该服务器自动下载并缓存到`C:\Symbols`目录。

2.  **设置可执行文件路径 (`.exepath`)**：此命令指定`.exe`和`.dll`文件的位置，有助于WinDbg解析更完整的调用栈。
    ```text
    .exepath D:\CrashAnalysis
    ```

3.  **重新加载符号 (`.reload`)**：应用上述路径配置，强制加载所有模块的符号。
    ```text
    .reload /f
    ```
    *   `/f` 参数表示强制重新加载所有符号。

### 🔍 第四步：核心分析流程——“破案三板斧”

路径配置完成后，就可以开始分析崩溃原因了。

1.  **第一板斧：切换到崩溃上下文 (`.ecxr`)**：这个命令至关重要，它会将调试上下文切换到**发生异常的那个时刻**，让你能精准地看到崩溃现场。
    ```text
    .ecxr
    ```

2.  **第二板斧：查看详细调用栈 (`k` 系列命令)**：查看崩溃时的函数调用序列，找出是哪个函数引发了问题。
    *   `k`：显示简单的调用栈。
    *   `kb`：显示调用栈及前三个参数。
    *   `kp` / `kP`：显示完整的函数参数。
    *   `kn`：显示带栈帧编号的调用栈，便于后续切换帧。
    *   `~*k`：显示**所有线程**的调用栈，用于排查崩溃是否由其他线程引起。

    在`k`命令的输出中，重点查找属于**你自己项目**的模块（如 `MyApp!...`），它旁边的源码行号（`[...]`内）就是关键线索。

3.  **第三板斧：自动分析报告 (`!analyze -v`)**：让WinDbg引擎自动给出一个全面的诊断报告。
    ```text
    !analyze -v
    ```
    重点关注输出中的以下信息：
    *   **`FAULTING_IP`**：发生崩溃的那条指令地址。
    *   **`EXCEPTION_RECORD`**：异常记录，`ExceptionCode`字段（如 `0xC0000005` 表示“访问违例”）是重要线索。
    *   **`PROBLEM_CLASS`**：问题分类。
    *   **`STACK_TEXT`**：调用栈文本，是定位问题的核心。

### 🛠️ 第五步：高级分析命令（深入调查）

如果“三板斧”没能直接解决问题，可以用以下命令进行更深入的调查。

*   **查看局部变量 (`dv`)**：在通过 `kn` 定位到嫌疑函数后，先用 `.frame` 切换到对应的栈帧，再用 `dv` 查看该函数的局部变量。
    ```text
    .frame 1  // 切换到编号为1的栈帧
    dv /t /v  // 显示所有局部变量的类型、地址和值
    ```
    > **注意**：对于Release版本的程序，局部变量可能被优化掉，导致`dv`命令信息不全。

*   **检查数据结构 (`dt`)**：查看特定变量或数据结构的内容。
    ```text
    dt 变量名
    ```

*   **检查内存 (`d` 系列命令)**：以不同格式查看指定地址的内存内容。
    ```text
    dd 地址   // 以双字（4字节）显示
    dq 地址   // 以四字（8字节）显示
    da 地址   // 以ASCII字符串显示
    du 地址   // 以Unicode字符串显示
    ```

*   **查看模块信息 (`lm`)**：列出所有已加载的模块，并验证符号是否加载成功。
    ```text
    lm          // 列出所有模块
    lm vm MyApp // 显示名为"MyApp"的模块的详细信息
    ```
    在输出中，确认 `Symbol status` 是否为 `Symbols loaded`。

### 🧐 常见问题与排查

*   **符号加载失败 (`Symbols not found`)**：
    1.  确认 `.pdb` 文件路径是否正确。
    2.  **最关键**：检查 `.pdb` 文件是否与 `.exe`/`.dll` **版本匹配**（时间戳一致）。
    3.  检查网络，确保能访问微软符号服务器（`msdl.microsoft.com`）。
*   **看不到自己代码的调用栈**：
    1.  确认已通过 `.exepath` 正确设置了可执行文件路径。
    2.  确保所有相关的 `.exe` 和 `.dll` 文件都已准备好。
*   **`!analyze -v` 输出信息不足**：
    1.  尝试使用 `.ecxr` 切换到异常上下文后再执行 `!analyze -v`。
    2.  检查Dump文件类型，如果是“小型转储”(Minidump)，可能信息有限。
