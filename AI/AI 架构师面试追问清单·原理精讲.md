# AI 架构师面试追问清单 · 原理精讲版

> 使用指南：每个问题都有“面试怎么说”和“为什么是这样”两部分。掌握原理不是背概念，而是能解释“设计时的取舍”“底层运行机制”和“边界条件”。建议先理解原理，再对着面试话术用自己的话讲一遍。

---

## 一、AI Agent / 智能体

### Q1 讲讲你的浏览器 AI 助手，一轮完整流程是什么？

**面试怎么说**：
> “用户发一句话进来，我先把系统提示词和可用工具的说明书拼成上下文，发给大模型。大模型返回它想调用的工具，我先做权限检查——只读的直接执行，有副作用的弹窗让用户确认。执行完把结果塞回对话，再发给大模型，它决定下一步。这样循环直到大模型觉得任务完成，直接回复文字给用户。整个循环我用 Rust + tokio 实现的。”

**🧠 掌握原理**  
Agent 执行循环的本质是 **ReAct 模式 (Reasoning + Acting)**。模型不是一步到位输出最终答案，而是在“思考”和“行动”之间交替：每收到一个观察（工具返回结果），重新推理下一步动作。可以理解为将 **马尔可夫决策过程** 简化为：`状态(对话历史) → 动作(工具调用) → 奖励(任务完成信号)`。  
工程上，循环中止条件来自三种信号：模型输出终止 token、达到最大步数、外部中断。理解这个循环，就能明白为什么工具描述必须清晰、上下文窗口要管理——每一步的决策都依赖前一步的信息完整性。

---

### Q2 Agent 死循环怎么办？比如反复调同一个工具？

**面试怎么说**：
> “三层防护：第一层硬上限，最大迭代次数到了就停；第二层工具级超时，单个工具卡住不拖累全局；第三层重复检测，相同参数连续调用 N 次就暂停问用户。”

**🧠 掌握原理**  
死循环本质是策略函数陷入了“吸引子”——局部最优动作重复执行。检测依靠 **动作签名哈希**：将 `{tool_name, parameters}` 计算哈希值，在一个滑动窗口内命中次数超过阈值则判定为循环。这种停滞检测广泛用于规划系统。配合用户中断，构成了人和 AI 共享控制权的安全机制，即 **human-in-the-loop**。理解原理后，你就能设计出更细致的循环检测，例如参数变化但语义相同的调用也能被识别。

---

### Q3 24 条消息/64KB 滑动窗口，为什么是这个数？

**面试怎么说**：
> “大模型上下文窗口 128K token，但系统提示词、工具定义要占掉一半，留 64KB 给对话历史是安全水位。超了就把中间的旧消息裁掉，但保留首条任务目标和最近几轮操作结果。摘要压缩是个好方向，但可能丢失关键细节，目前裁剪更安全。”

**🧠 掌握原理**  
上下文窗口由 Transformer 的自注意力机制决定，每个 token 需要与之前所有 token 计算注意力，因此内存和计算复杂度随长度平方增长。滑动窗口裁剪本质是 **FIFO 淘汰**，但需保留“锚点消息”（如系统提示、初始任务），因为模型依赖任务目标维持行为一致性。若使用摘要，会引入信息压缩的有损性，需要在召回率和准确率之间权衡。这背后是 **记忆管理策略**：保留最重要的长短期信息。

---

### Q4 Chat 模式和 Agent 模式有什么区别？为什么不能都用 Agent 模式？

**面试怎么说**：
> “Chat 模式只读不动手，Agent 模式能执行有副作用的操作。只读操作可以自动跑，写操作必须弹窗确认。不能用 Agent 模式处理一切，因为频繁确认会打扰用户，而且权限最小化原则能减少误操作风险。”

**🧠 掌握原理**  
这是 **权限分级** 和 **操作安全性** 的体现。系统将工具标记为 `read-only`（纯函数，无副作用）和 `destructive`（改变外部状态）。只读操作可以安全地自动执行，类似函数式编程的无副作用保证；而写操作必须获得用户一次性授权，防止自动化造成的无法回滚的错误。这背后是 **最小权限原则**——只授予完成任务所必需的最小权限。

## 二、MCP 协议

### Q5 MCP 解决了什么问题？和 Function Calling 有什么区别？

**面试怎么说**：
> “Function Calling 是模型层的能力，但每家的工具定义格式不同。MCP 是协议层的标准化，规定了工具怎么注册、被发现、被调用。我的工具服务写一次，任何支持 MCP 的 Agent 都能接。”

**🧠 掌握原理**  
Function Calling 是模型供应商定义的 API 契约，与模型强绑定，如 OpenAI 的 `tools` 数组。MCP 则是 **客户端-服务器协议**，基于 JSON-RPC，定义了 `tools/list`、`tools/call` 等标准方法。这就像 ODBC 统一了数据库访问，MCP 将工具抽象为资源，通过 **能力发现** 动态绑定，解除模型与工具的耦合。理解协议分层，就能明白为何 MCP 可以跨模型复用工具。

---

### Q6 Streamable HTTP 和 stdio 传输的区别？为什么选 HTTP？

**面试怎么说**：
> “stdio 是本地进程间管道通信，简单低延迟但一对一。Streamable HTTP 支持远程、多客户端、断线重连，适合工具服务化部署。我的 MCP 服务要开放给多个 Agent 使用，所以选 HTTP。”

**🧠 掌握原理**  
stdio 传输本质是父子进程间的标准 I/O 重定向，没有网络协议开销，但进程生命周期强绑定。Streamable HTTP 基于 HTTP 的流式响应和 SSE，可以在无状态 HTTP 上实现服务端推送。它支持 **连接多路复用**，一个工具服务器可以同时服务多个 Agent，并且可以通过负载均衡横向扩展。选型时在“延迟”和“可扩展性”之间做了取舍，这反映了分布式系统设计中的经典权衡。

---

### Q7 MCP 的安全风险有哪些？

**面试怎么说**：
> “工具投毒——工具描述里藏恶意指令，AI 可能照做；偷换概念——工具版本更新后行为变了；数据外泄——用户敏感数据被当作参数传出。我的应对是工具审核、版本锁定、权限分级和审计日志。”

**🧠 掌握原理**  
工具投毒属于 **间接提示注入**，攻击面不在用户输入，而在工具返回内容或工具描述。由于 LLM 无法区分指令来源的可信度，必须在外围建立信任边界。解决方案包括 **签名验证、内容安全过滤、人工审批流**。数据外泄的防范则是通过隐私数据识别和脱敏网关，在调用前对参数进行过滤。这本质是在 LLM 不可信的前提下构建 **纵深防御**。

## 三、Function Calling

### Q8 tool schema 怎么设计？

**面试怎么说**：
> “工具名用动词，描述写清楚什么情况下该用、什么情况下不该用，参数给示例。好的说明书写清楚上下文，AI 才能选对。”

**🧠 掌握原理**  
Tool schema 是 LLM 的 **先验知识**，直接影响其规划能力。模型通过函数描述来选择工具，这类似于 **检索式规划**：模型在 prompt 中匹配工具描述与当前意图。因此，必须提供足够的语义信息和反面指令（何时不使用），以减少 false positive。参数约束（type、enum、description）会被转换为结构化输出约束，一些框架会在采样阶段施加 grammars 保证格式合法。

---

### Q9 并行工具调用支持吗？

**面试怎么说**：
> “目前主要是串行，模型调一个工具，我执行完返回结果再让它决定下一步。并行执行多个无依赖的工具调用是优化方向，可以减少往返轮次。”

**🧠 掌握原理**  
从模型侧看，一次返回多个 `tool_calls` 意味着它认为这些动作可以独立执行。调度器需要解析 **依赖图**：如果两个工具调用无数据依赖（参数不依赖于另一个的输出），就可以并发执行。并发带来吞吐提升，但增加了错误处理的复杂性。很多框架已支持基于有向无环图的并行执行，实质是 **异步任务编排**。

---

## 四、RAG / ChromaDB

### Q10 RAG 完整链路是什么？

**面试怎么说**：
> “建库时把文档切成 chunk，生成 embedding 存入 ChromaDB。查询时把用户问题向量化，检索 top-k 最相似片段，拼到提示词里让模型基于资料回答。”

**🧠 掌握原理**  
RAG 的核心是利用 **语义向量空间** 进行近似最近邻搜索。embedding 模型将文本映射到高维向量，使得语义相近的文本向量距离近。检索时通过余弦相似度或内积度量距离，ANN 索引（如 HNSW）实现亚线性时间检索。chunk 大小直接影响检索粒度和上下文完整度，重叠窗口则是为了防止切断关键语义。这是信息检索与语言模型的结合：检索提供证据，生成提供表达。

---

### Q11 检索不准怎么排查？

**面试怎么说**：
> “切分太碎导致信息不全，用户措辞和文档不同导致向量匹配差，embedding 模型领域不匹配。我加 BM25 做混合检索，建评测集定量验证。”

**🧠 掌握原理**  
向量检索擅长捕捉语义，但会忽略精确关键词匹配；BM25 基于词频统计正好弥补这点。混合检索将两者分数加权求和，再通过重排序模型（cross-encoder）精排，这是现代检索系统的标准架构。排查时，通过失败案例的 query-document 可视化分析相似度分布，判断是 embedding 模型问题还是 chunk 策略问题。**评测集驱动的优化**确保每次改动都有量化依据。

---

### Q12 短期记忆和长期记忆怎么分工？

**面试怎么说**：
> “短期记忆是当前会话的对话历史，长期记忆是跨会话的用户信息，存在 ChromaDB 里按 user_id 隔离。每次对话开始检索历史记忆放入上下文。”

**🧠 掌握原理**  
这模仿了人类的 **记忆架构**：工作记忆处理当前信息，长时记忆存储持久化知识。在 Agent 中，短期记忆即上下文窗口，容量有限；长期记忆通过向量数据库持久化，依据相关性检索，突破窗口限制。隔离通过命名空间实现，每个用户独立 collection，确保记忆不跨用户污染，符合多租户数据安全要求。

---

## 五、LLM 多模型适配 / Token 成本

### Q13 统一适配层怎么设计？

**面试怎么说**：
> “定义统一的 chat 接口，每家写一个 adapter，内部翻译成各自的 API 格式。差异最大的是工具定义和流式事件格式。”

**🧠 掌握原理**  
适配器模式 (Adapter Pattern) 在这里用于 **接口标准化**。每家 LLM 提供商的请求/响应结构都不同，适配层将其包装成统一的 `ChatCompletion` 对象。关键挑战在于流式响应的差异：OpenAI 用 `delta` 累积，Anthropic 用不同内容块类型。适配器内部需实现事件类型映射和增量内容拼接，向上层暴露一致的 `AsyncIterator`，实现模型可插拔。

---

### Q14 模型选型怎么做？

**面试怎么说**：
> “我在适配层做了路由——规划任务用强模型保证准确率，简单分类用便宜模型省钱，隐私数据走本地模型。配合用量统计做数据驱动的选型。”

**🧠 掌握原理**  
模型路由本质是一个 **多臂老虎机** 决策问题：在成本、延迟、质量之间动态平衡。实现时，预先为每个任务类型定义最低能力要求（如逻辑推理、工具调用），然后构建决策矩阵将请求分配到满足条件的成本最低模型上。路由规则可基于规则引擎或轻量分类模型，构成 LLMOps 的成本控制核心。

---

### Q15 缓存命中是什么意思？

**面试怎么说**：
> “把不变的系统提示词和工具定义放前面，变化部分放后面，可以命中 prompt caching，前缀相同部分只收一折。”

**🧠 掌握原理**  
LLM 推理时会对已计算的 token 缓存 KV 状态。如果新请求的前缀与之前一致，可以复用缓存，跳过这部分计算。命中与否取决于前缀的字节级匹配，因此保持工具定义顺序、系统提示词静态不变至关重要。缓存命中率 = 缓存 token 数 / 总输入 token 数，是成本优化关键指标。

---

## 六、Ollama / 本地部署

### Q16 本地模型什么场景用？什么规格？

**面试怎么说**：
> “处理隐私数据、内网环境用 Ollama 部署 Qwen2.5-7B Q4 量化，单次回复 2-3 秒，跑在 RTX 4090 上。”

**🧠 掌握原理**  
量化通过降低权重精度（如 float16→int4）减少模型大小和计算量，但会引入精度损失。Q4 量化使 7B 模型显存需求从 ~14GB 降至 ~4GB，单卡可推理。推理分为预填充（并行处理输入 prompt）和自回归解码（串行生成 token），延迟主要由解码阶段决定。理解这些才能评估本地模型的可行性边界。

---

### Q17 本地模型能力弱怎么办？

**面试怎么说**：
> “减少工具选项、说明书写得更细、拆小步、混合架构——本地做简单任务，复杂任务转发云端。”

**🧠 掌握原理**  
小模型 capacity 有限，在规划这种需要强推理能力的任务上表现下降。工程上通过降低任务复杂度（任务分解）来适配模型能力边界。混合架构利用本地模型处理低延迟、隐私敏感任务，云端模型处理需要深度推理的任务，构成 **级联推理系统**，在延迟、成本和质量间取得平衡。

## 七、Prompt Engineering

### Q18 举一个优化提示词的实际案例

**面试怎么说**：
> “AI 经常点错商品，我在提示词里加了操作前先 snapshot 检查元素、不要盲目点击的规则，并给了 2 个正例 1 个反例，准确率从约 60% 提到 85%。”

**🧠 掌握原理**  
这利用了 **In-Context Learning** 和 **思维链**。通过示例直接调整模型的条件概率分布，比改参数更轻量。反例能有效抑制错误的推理路径。本质是在前缀中注入约束，引导模型的自回归生成，使其倾向于遵循检查步骤而非直接执行。

---

### Q19 怎么系统化调 prompt？

**面试怎么说**：
> “建一个 50 条典型问题的评测集，修改 prompt 前后跑一遍对比通过率，像管理代码一样用 Git 管理 prompt 版本。”

**🧠 掌握原理**  
这引入了 **ML 实验管理** 的思想：通过 hold-out 验证集评估 prompt 效果，避免“调了一个 case 又坏了另一个”。评测指标可以细化为任务成功率、步骤准确率等。结合统计检验可以判断提升是否显著。这证明了你不是凭感觉调参，而是用工程方法处理自然语言的模糊性。

---

## 八、Agent 评测与可观测性

### Q20 Trace 回放是什么？

**面试怎么说**：
> “像飞机黑匣子，记录每一步的输入、模型返回、工具调用和耗时。失败时回放 trace 定位是规划错、执行错还是环境问题。”

**🧠 掌握原理**  
Trace 是 **分布式追踪** 在 Agent 领域的应用。将一次任务分解为多个 span（规划、工具调用等），通过 traceId 串联。可观测性三支柱：日志（事件记录）、指标（聚合数据）、追踪（请求级链路）。复现失败时，重放同样的上下文和工具返回（需 mock 外部依赖），可以确认为逻辑错误还是环境随机性。

---

### Q21 评测指标有哪些？

**面试怎么说**：
> “任务成功率、平均轮数、token 成本、步骤准确率。大模型不稳定所以多次跑取平均，评测时 temperature 设为 0。”

**🧠 掌握原理**  
temperature=0 使模型采用贪心解码，输出确定，保证评测可复现。指标之间需要权衡，例如提高成功率可能增加轮数和成本。建立综合评分（如 success×(1/cost)）可以指导优化方向。这背后是 **多目标优化** 思想。

---

## 九、Transformer / CNN 原理

### Q22 大白话讲注意力机制，Q/K/V 是什么？

**面试怎么说**：
> “Q 是你想找的内容，K 是每本书的标签，V 是书的内容。用 Q 和 K 做对比，按匹配度加权融合 V。缩放点积除以 √d_k 是防止点积值太大导致 softmax 后概率两极分化。”

**🧠 掌握原理**  
自注意力公式：`Attention(Q,K,V) = softmax(QK^T / √d_k) V`。`QK^T` 的方差会随维度 d_k 增长而变大，经过 softmax 后梯度会集中在极少数位置，模型难以学习。除以 √d_k 使方差稳定为 1，保持梯度平滑，这是 Xavier 初始化的思想延伸。注意力机制的本质是让每个位置动态地聚合全局信息，打破了 RNN 的顺序束缚。

---

### Q23 反向传播和梯度消失怎么讲？

**面试怎么说**：
> “反向传播就是把误差从最后一层往前面传，求每层参数对误差的贡献。梯度消失就是传着传着信号没了。ReLU 能缓解，因为正区梯度恒为 1；残差连接提供高速公路；LayerNorm 稳定分布。”

**🧠 掌握原理**  
反向传播的核心是 **链式法则**。当激活函数用 sigmoid 时，其导数最大为 0.25，多层连乘后指数衰减。ReLU 导数在正区为 1，避免连乘衰减（但会引入 Dead Neuron）。残差连接改变了梯度流：`y = F(x) + x`，反向时梯度可直接通过恒等映射传播，即使 F(x) 梯度很小，也能维持有效学习。这是深层网络成功的关键。

---

### Q24 Transformer 为什么比 RNN 适合并行？

**面试怎么说**：
> “RNN 必须按顺序处理，第二个词依赖第一个词的计算结果。Transformer 自注意力一次性算所有词的配对关系，可以并行。位置编码补上了顺序信息。”

**🧠 掌握原理**  
RNN 的时间步间存在 **循环依赖**，展开的计算图是串行链，无法并行。Transformer 的自注意力矩阵 `QK^T` 一次性计算所有 token 对的相似度，矩阵乘法高度并行，适合 GPU。位置编码通过正弦函数或可学习向量为每个位置注入绝对/相对位置信息，使得置换不变性的自注意力获得序列建模能力。

## 十、Rust 系统编程

### Q25 为什么用 Rust 不用 Node/Python？

**面试怎么说**：
> “Rust 编译成单个可执行文件，没有运行时依赖；没有 GC，不会出现停顿；性能接近 C，处理并发消息开销极低。”

**🧠 掌握原理**  
Rust 的所有权系统和借用检查器在编译期保证内存安全，无需垃圾回收，因此运行时延迟可预测。async/await 基于无栈协程，状态机在编译时确定大小，可以在栈上分配，切换开销极低。单二进制分发借助静态链接，适合桌面端工具。

---

### Q26 tokio 和协程什么关系？

**面试怎么说**：
> “协程是轻量级任务，tokio 是 Rust 的异步运行时，提供事件循环和任务调度。async/await 把函数编译成状态机，遇到 .await 就挂起让出线程。”

**🧠 掌握原理**  
tokio 使用 **Reactor 模式**，I/O 事件触发 Waker 唤醒对应任务。每个 async 函数被编译为实现了 `Future` trait 的匿名结构体，`poll` 方法驱动状态转换。阻塞操作必须用 `spawn_blocking` 移到线程池，否则会阻塞事件循环，导致所有任务停止调度。理解这一点才能设计高并发系统。

## 十一、AI 辅助编程 / 研发提效

### Q27 AI 在工作流里具体怎么用？哪些环节 AI 做不了？

**面试怎么说**：
> “AI 负责写脚手架、CRUD、测试初稿、CSS。架构决策、安全逻辑、Code Review、线上排查必须人做。我的角色是决策者和审查者。”

**🧠 掌握原理**  
AI 擅长模式匹配和模板生成（基于大量训练），但缺乏对业务全局状态的建模和因果推理能力。安全相关代码的错误可能导致灾难性后果，AI 无法理解法律和业务约束，因此必须人工审查。这是一种 **协同智能** 模式：人做判断和策略，AI 做执行加速，类似半自动驾驶。

### Q28 AI 生成代码出过事故吗？

**面试怎么说**：
> “AI 生成的鉴权代码漏了数据权限检查，导致 A 用户能看到 B 用户的数据，review 时发现并拦截了。”

**🧠 掌握原理**  
这是典型的 **越权漏洞**（IDOR）。AI 倾向于实现“功能性”需求而忽略“约束性”需求（如权限边界），因为训练数据中功能性代码更多。通过这个案例理解大模型的安全盲区：它不理解数据所有权的业务语义，需要人工在关键路径上设立安全门禁。

**🧠 掌握原理**

### Q30 设计一个“AI 客服 + 工单系统”，架构怎么画？

# AI技术能力原理

## 1. Agent 执行引擎
**Rust + tokio 实现 Chat/Agent 双模式、Function Calling、上下文滑动窗口（24条/64KB）、执行追踪、死循环检测**

### 核心数学结构
Agent 可以建模成一个 **ReAct 循环**，状态转移由函数 \( f \) 决定：
\[
\text{state}_{t+1} = f(\text{context}_t, \text{action}_t)
\]
其中 \(\text{context}_t = [\text{system\_prompt}, m_1, m_2, \dots, m_t]\) 是当前对话历史。

- **滑动窗口**：  
  上下文窗口大小固定，我们保留最近的 \( L \) 条消息和一个锚点（首条任务）。
  \[
  \text{context}_t = \text{Truncate}(\text{history}, W)
  \]
  裁剪函数：  
  - 保留索引 \(0\) 和 \([t-L+1, t]\) 的消息  
  - 总 token 数 ≤ \(C_{\max} = 64\text{K}\)（用分词器实时计数）

- **Function Calling**：  
  模型输出一个工具调用 \(a_t = (\text{tool\_name}, \text{params})\)，动作空间由可用工具集合 \(\mathcal{T}\) 定义。  
  执行后得到观察 \(o_t = \text{execute}(a_t)\)，拼接回上下文：
  \[
  m_{t+1} = \text{assistant}(a_t), \quad m_{t+2} = \text{user}(o_t)
  \]

- **死循环检测**：  
  将动作序列映射为签名向量：
  \[
  s_t = \text{Hash}(\text{tool\_name}, \text{params})
  \]
  在滑动窗口 \(W_d\)（如最近 5 步）内统计签名频率。如果连续 \(k\) 步（如 3 步）的签名完全相同，即：
  \[
  \max_{i} \text{count}(s_i \in W_d) \ge k \implies \text{循环告警}
  \]
  这本质是 **吸引子检测**，防止策略函数陷入局部死循环。

- **执行追踪**：  
  记录每条 trace：\(\{(t, \text{input\_tokens}, \text{output\_tokens}, \text{tool\_latency}, \text{status})\}\)。整个任务的总成本：
  \[
  C = \sum_{i} (P_{\text{in}} \cdot \text{tokens\_in}_i + P_{\text{out}} \cdot \text{tokens\_out}_i)
  \]
  追踪让你能按 \(C\) 和成功率做优化。

## 2. MCP 协议开发
**Streamable HTTP 端点工具发现与调用，权限自动分级，敏感操作人工确认**

### 形式化定义
MCP 基于 **JSON-RPC 2.0**，核心是两个原语：
- **工具发现**：客户端请求 `tools/list`，服务器返回工具集合
  \[
  \mathcal{T} = \{t_i = (\text{name}, \text{description}, \text{inputSchema}, \text{permission})\}
  \]
- **工具调用**：客户端发送 `tools/call`，携带工具名和参数，返回结果。

**权限分级** 用二元谓词判断：
\[
\text{IsSensitive}(t) = 
\begin{cases}
1 & \text{if } t.\text{type} \in \{\text{write, delete, execute}\} \\
0 & \text{otherwise}
\end{cases}
\]
当 \(\text{IsSensitive}(t) = 1\) 时，系统不直接执行，而是触发人工确认的 **中断协议**：
\[
\text{confirmation\_token} = \text{RequestUserConsent}(t, \text{params})
\]
只有收到带有效 token 的确认请求，才实际执行。

这构成一个 **带守卫的有限状态机**：
- 自动执行状态：权限为 read-only
- 等待状态：等待用户确认
- 执行状态：得到授权后执行

数学上，这确保了系统的安全性——所有状态转移都有明确的守卫条件。

## 3. 多模型适配层
**OpenAI / Anthropic / DeepSeek / Ollama 统一接口（adapter 模式），流式输出、Token 统计、模型路由**

### 适配层数学
我们定义一个统一接口 \(I\)：
\[
\text{chat}(\text{messages}, \text{tools}) \rightarrow (\text{text}, \text{tool\_calls})
\]
\[
\text{stream}(\text{messages}) \rightarrow \text{AsyncIterator}[\text{delta}]
\]
每个模型提供商实现一个适配器 \(A_m\)，将统一请求转换为各家的 API 格式：
\[
\text{request}_m = A_m.\text{encode}(\text{messages}, \text{tools})
\]
响应再被解码回统一格式。

- **Token 统计**：  
  每个请求的 token 数：
  \[
  N_{\text{prompt}} = \text{tokenizer}(\text{messages}), \quad N_{\text{completion}} = \text{len}(\text{output\_tokens})
  \]
  成本函数为：
  \[
  \text{Cost} = N_{\text{prompt}} \cdot c_{\text{in}}^m + N_{\text{completion}} \cdot c_{\text{out}}^m
  \]
  其中 \(c^m\) 是模型 \(m\) 的单价。

- **模型路由**：  
  任务被分为多个类别（规划、摘要、隐私等）。路由就是求解一个约束优化问题：
  \[
  \min_{m \in \mathcal{M}} \text{Cost}(m, \text{task}) \quad \text{s.t.} \quad \text{Capability}(m) \ge \text{Required}(\text{task})
  \]
  能力矩阵 \(\text{Capability}\) 根据基准测试预先定义（如工具调用能力、推理能力）。对于隐私任务，增加约束 \(m\) 必须在本地部署，即 \(m \in \mathcal{M}_{\text{local}}\)。

- **流式输出**：  
  每个 SSE 事件携带一个 token 的增量 \(\Delta\)，最终文本由拼接得到：
  \[
  \text{text} = \sum \Delta_i
  \]

## 4. RAG 与记忆系统
**文档切分 → embedding → ChromaDB → top-k 检索；短期/长期向量记忆，多用户隔离**

### 向量空间的数学本质
**建库**：  
每个文档被切分成块 \(c_i\)，通过嵌入函数 \(E\) 映射到向量空间 \(\mathbb{R}^d\)：
\[
v_i = E(c_i) \in \mathbb{R}^d
\]
所有向量存入 ChromaDB，构建近似最近邻（ANN）索引。

**检索**：  
用户查询 \(q\) 同样被嵌入为 \(v_q\)，检索 top-\(k\) 依据余弦相似度：
\[
\text{sim}(v_q, v_i) = \frac{v_q \cdot v_i}{\|v_q\| \|v_i\|}
\]
可以理解为在高维空间中找角度最小的向量。混合检索时，融合 BM25 分数 \(s_{\text{BM25}}\)：
\[
s_{\text{final}} = \alpha \cdot \text{sim} + (1-\alpha) \cdot s_{\text{BM25}}
\]
然后按 \(s_{\text{final}}\) 重排，取前 \(k\) 个。

**记忆隔离**：  
长期记忆按用户 ID 分区，每个用户 \(u\) 拥有独立的集合 \(\mathcal{V}_u\)。查询时只在当前用户的向量空间内搜索：
\[
v_i \in \mathcal{V}_u
\]
用元数据过滤实现，即 \( \text{where: \{user\_id: u\}} \)。这保证了记忆的 **租户隔离**。

**短期 vs 长期**：  
- 短期记忆：当前会话的消息序列 \( [m_1, \dots, m_t] \)，完全保留在上下文窗口。
- 长期记忆：在每次会话开始时，从 \(\mathcal{V}_u\) 中检索与初始任务最相关的 top-\(l\) 个记忆块，拼接到系统提示词中。

整个过程就像：
\[
\text{Answer} = \text{LLM}(\text{query} + \underbrace{[m_1,\dots,m_t]}_{\text{短期}} + \underbrace{\text{Retrieve}(q, \mathcal{V}_u)}_{\text{长期}})
\]

## 5. 模型原理工程化
**NumPy 手写 Q/K/V 注意力计算、softmax 缩放、卷积，自研 Canvas 2D 渲染引擎可视化**

### 注意力就是矩阵乘法
核心公式：
\[
\text{Attention}(Q, K, V) = \text{softmax}\!\left(\frac{Q K^T}{\sqrt{d_k}}\right) V
\]
逐层拆解：
- 输入：\(X \in \mathbb{R}^{n \times d_{\text{model}}}\)
- 投影：\(Q = X W^Q, \; K = X W^K, \; V = X W^V\)，其中 \(W^* \in \mathbb{R}^{d_{\text{model}} \times d_k}\)
- 注意力分数矩阵：\(S = \frac{Q K^T}{\sqrt{d_k}}\)，形状 \([n, n]\)，每个元素 \(s_{ij}\) 是第 \(i\) 个查询与第 \(j\) 个键的相似度。
- 缩放因子 \(\sqrt{d_k}\) 的数学原因：假设 \(q,k\) 各分量独立且方差为 1，点积方差为 \(d_k\)。除以 \(\sqrt{d_k}\) 将方差拉回 1，防止 softmax 进入饱和区，梯度不至于消失。
- softmax 逐行归一化：\(A = \text{softmax}(S)\)，使得 \(\sum_j A_{ij} = 1\)。
- 输出：\(O = A V\)，每个位置的输出是所有 \(V\) 的加权和。

### 卷积（CNN 基础）
2D 卷积的互相关操作：
\[
Y_{i,j} = \sum_{u=-k}^{k} \sum_{v=-k}^{k} X_{i+u, j+v} \cdot F_{u,v} + b
\]
通过 NumPy 实现时，本质上就是四重循环或 im2col 变换成矩阵乘法。

### 可视化引擎
自研 Canvas 2D 渲染引擎通过矩阵变换实现坐标系统：
\[
\begin{bmatrix} x' \\ y' \\ 1 \end{bmatrix} = 
\begin{bmatrix} a & b & t_x \\ c & d & t_y \\ 0 & 0 & 1 \end{bmatrix}
\begin{bmatrix} x \\ y \\ 1 \end{bmatrix}
\]
用于将计算图中的张量形状、数据流动画化，把抽象矩阵运算转为可视图形。

## 6. 工程化与测试
**Playwright 冒烟测试、Rust 集成测试、pytest + GitHub Actions CI/CD 自动发布 PyPI**

### 测试与交付的数学建模
- **冒烟测试**：定义一组关键路径的断言集合 \(\mathcal{T}_{\text{smoke}}\)，每个测试验证系统基本功能。冒烟通过的条件是：
  \[
  \forall t \in \mathcal{T}_{\text{smoke}}, \; t.\text{status} = \text{pass}
  \]
  否则阻止合入。

- **CI/CD 流水线**：  
  构建过程可视为有向无环图（DAG），节点包括：代码检出 → 依赖安装 → 单元测试 → 集成测试 → 构建制品 → 发布。  
  成功发布的条件是：
  \[
  \bigwedge_{i \in \text{stages}} \text{stage}_i = \text{success}
  \]
  任一阶段失败则停止下游，这是 fail-fast 策略。

- **自动化发布 PyPI**：  
  在 tag 推送时触发 workflow，执行：
  \[
  \text{build} \rightarrow \text{twine upload}
  \]
  整个流程用 GitHub Actions 的 YAML 定义，本质是事件驱动的状态机：`push tag` 事件启动一个作业，根据退出码决定成功或失败。

- **测试金字塔**的数量比例：大量单元测试（快速、隔离）、少量集成测试、极少端到端测试，这可通过成本与反馈速度的权衡来理解：
  \[
  \text{Optimal} = \arg\min (\text{cost} + \lambda \cdot \text{bug\_escape\_rate})
  \]

每个环节都不是孤立的知识点，而是一条完整的 **AI 系统设计逻辑链**。当你能够从原理上解释每一个“为什么”，面试就不再是问答，而是你展示领域深度的舞台。
